#  Система записи пациентов к врачам (МИС)

**Ссылка на развернутый сайт (Frontend):** [https://doctor-appointment-system-frontend-henna.vercel.app/](https://doctor-appointment-system-frontend-henna.vercel.app/)

**Медицинская информационная система** предназначена для автоматизации расписания и цифровизации онлайн-записи. Проект устраняет ручную организацию графиков, минимизирует ошибки человеческого фактора и повышает прозрачность доступности врачей клиники в реальном времени.

###  Ключевой функционал модулей ИС:
* **Онлайн-запись:** Самостоятельный выбор специалиста, категории медицинской услуги и свободного 30-минутного интервала.
* **Электронная медкарта:** Доступ врачей к цифровой истории болезни пациента (диагнозам и назначениям) до начала приёма.
* **Управление расписанием:** Блокировка слотов администратором на время отпусков и контроль общей загрузки клиники.
* **Коммуникации:** Встроенный чат для предварительных консультаций между врачом и пациентом, а также отправка напоминаний.

##  Инструкция по локальному запуску бэкенд-сервера

Проект разработан в рамках слоистой архитектуры на базе асинхронного веб-фреймворка **FastAPI** и реляционной СУБД **SQLite**.

###  1. Подготовка окружения и зависимостей
Убедитесь, что на компьютере установлен Python 3.8+. Установите необходимые пакеты и библиотеки одной командой в терминале (командной строке):
```bash
python -m pip install fastapi uvicorn pydantic email-validator
```

###  2. Инициализация базы данных
Если файл базы данных `medical.db` отсутствует или его необходимо обновить до исходного тестового состояния (11 заявок, 8 пользователей по ролям, 4 категории), запустите локальную утилиту SQLite:
```bash
./sqlite3.exe medical.db < schema.sql
./sqlite3.exe medical.db < seed.sql
```

###  3. Запуск веб-сервера
Запустите сервер автоматической перезагрузки приложения `Uvicorn` из корневого каталога проекта:
```bash
python -m uvicorn app.main:app --reload
```
*После успешного запуска сервер начнет принимать запросы по адресу `http://127.0.0.1:8000`.*

###  4. Интерактивное тестирование сценариев (Swagger UI)
Перейдите в браузере по ссылке:
 **[http://127.0.0](http://127.0.0.1:8000/docs#/)**

Перед вами откроется встроенная интерактивная документация **Swagger UI** со всеми реализованными пользовательскими сценариями (Авторизация по ОМС, Онлайн-запись, Поиск с LIKE-фильтрацией, Карточка приёма и Удаление записи). Каждую функцию можно протестировать вживую с отправкой реальных JSON-пакетов данных в базу.

##  Спецификация модульного API-слоя (REST API)

Бэкенд-сервер предоставляет структурированный REST API-интерфейс, разделенный на независимые изолированные модули с помощью `APIRouter`.

###  1. Локальный запуск и адреса
Убедитесь, что зависимости установлены, и запустите сервер автоматической перезагрузки из корня репозитория:
```bash
python -m uvicorn app.main:app --reload
```
* **Базовый URL локального сервера:** `http://127.0.0.1:8000`
* **Интерактивная документация (Swagger UI):** `http://127.0.0`
* **Спецификация OpenAPI (JSON-схема):** `http://127.0.0`

###  2. Список основных API Endpoints

####  Модуль: Управление Пользователями и Авторизация (`APIRouter`)
* `POST /api/v1/auth/login` — Авторизация пациента в МИС по 16-значному полису ОМС (**Экран 01**).
* `PUT /api/v1/users/{user_id}/contacts` — Обновление email и номера телефона в профиле (**Экран 05**).

####  Модуль: Управление Заявками и Расписанием Врачей (`APIRouter`)
* `GET /api/v1/appointments` — Получение общего реестра приёмов с поддержкой живого поиска по ФИО и фильтрацией через `Query`-параметры (`search`, `status_id`, `category_id`) (**Экран 02**).
* `POST /api/v1/appointments` — Резервирование нового 30-минутного временного слота онлайн-записи с проверкой накладок расписания и защитой от Race Condition (**Экран 03**).
* `DELETE /api/v1/appointments/{appointment_id}` — Безвозвратное удаление/отмена бронирования записи администратором с каскадным очищением чата (**Экран 05**).

---

###  3. Реальный пример API-запроса и ответа

#### Сценарий: Создание новой заявки онлайн-записи
* **HTTP Метод:** `POST`
* **Полный URL запроса:** `http://127.0.0`
* **Заголовки (Headers):** `Content-Type: application/json`

**Тело HTTP-запроса (JSON Request Body):**
```json
{
  "patient_id": 6,
  "doctor_id": 4,
  "category_id": 4,
  "datetime_slot": "2026-11-08 17:00"
}
```

**Тело успешного HTTP-ответа сервера (`201 Created`):**
```json
{
  "status": "created",
  "appointment_id": 12,
  "datetime_slot": "2026-11-08 17:00"
}
```

**Тело HTTP-ответа при ошибке Race Condition / Двойном бронировании (`409 Conflict`):**
```json
{
  "status": "error",
  "code": "SLOT_ALREADY_BOOKED",
  "message": "Конфликт бронирования: Этот временной слот у врача уже занят другим параллельным запросом.",
  "details": null
}
```

##  Инструкция по повторному деплою системы с нуля (Инфраструктурный гайд)

Данное руководство предназначено для быстрого восстановления, переразвертывания или переноса МИС на новый сервер/хост-машину в случае аварийного сбоя или обновления кодовой базы.

###  Сценарий А. Повторный деплой локально («Своя машина»)

Если вам необходимо полностью очистить систему, сбросить накликанные данные и запустить чистый контейнер с 11 эталонными записями, выполните следующие шаги:

1. **Полная остановка и уничтожение старого окружения:**
   Удаляет запущенный контейнер, изолированную сеть и очищает кэш образов:
   ```bash
   docker compose down --volumes --rmi local
   ```
2. **Очистка локального файла СУБД (Опционально):**
   Если вы хотите, чтобы при старте база данных пересобралась заново из SQL-скриптов, удалите старый бинарный файл на хост-машине:
   ```bash
   rm -f medical.db
   ```
3. **Инициализация конфигурации:**
   Убедитесь в наличии файла переменных окружения (при отсутствии скопируйте шаблон):
   ```bash
   cp .env.example .env
   ```
4. **Холодный запуск и автоматическая миграция:**
   Запустите сборку одной командой. Docker сам скачает Alpine Linux, установит `fastapi`, выполнит `schema.sql` и загрузит 11 приемов из `seed.sql`:
   ```bash
   docker compose up -d --build
   ```

###  Сценарий Б. Повторный деплой в удаленной среде (Облако Render)

Поскольку наш репозиторий GitHub напрямую интегрирован с облачным контуром Render, переразвертывание осуществляется по модели GitOps (Автоматически или В один клик).

#### Вариант 1. Автоматический деплой при обновлении кода (модель CI/CD)
1. Внесите необходимые изменения в исходный код на локальном компьютере.
2. Отправьте изменения в основную ветку разработки на GitHub:
   ```bash
   git add .
   git commit -m "build: критическое обновление бэкенда для пересборки"
   git push origin develop
   ```
3. **Результат:** Облако Render перехватит вебхук от GitHub, мгновенно остановит старый контейнер, скачает новый код, заново соберет Docker-образ и обновит приложение по вашему постоянному адресу.

#### Вариант 2. Ручной деплой с очисткой кэша (Через браузер)
Если код на GitHub не менялся, но вам нужно принудительно очистить контейнер и перезапустить инициализацию СУБД SQLite:
1. Авторизуйтесь в панели управления **[https://://render.com/](https://render.com/)**.
2. Выберите из списка ваш сервис **`doctor-appointment-system`**.
3. В правом верхнем углу нажмите на серую кнопку **`Manual Deploy`** (Ручной деплой).
4. В выпадающем меню выберите первый пункт: **`Clear cache and deploy`** (Очистить кэш и развернуть).
5. **Результат:** Облачный сервер сбросит старые бинарные слои и запустит чистую компиляцию Dockerfile. Через 1-2 минуты индикатор сменится на зеленый маркер **`Live`**, и обновленный пульт Swagger UI снова станет доступен по адресу: [https://doctor-appointment-system-90ta.onrender.com/docs](https://doctor-appointment-system-90ta.onrender.com/docs).

##  Автоматизация тестирования и CI/CD (Лабораторная работа №10)

В рамках проекта реализован полноценный программный комплекс автоматизированного регрессионного и интеграционного тестирования, покрывающий бизнес-логику ИС, регулярные выражения схем Pydantic и аппаратные UNIQUE-индексы СУБД.

###  1. Необходимые внешние зависимости (Requirements)
Для корректного развёртывания тестового окружения, парсинга сетевых пакетов и работы утилит автоматизации QA требуются следующие библиотеки Python:
*   **`pytest`** (версии `^8.0.0`) — базовый фреймворк автоматического поиска и выполнения тест-кейсов.
*   **`httpx`** (версии `^0.27.0`) — асинхронный HTTP-клиент, используемый тестовым контуром `fastapi.testclient.TestClient` для имитации сессий.
*   **`pydantic-settings`** (версии `^2.0.0`) — утилита сквозного перехвата инфраструктурных переменных окружения бэкенда.

###  2. Точная команда локального запуска тестов
Для проведения комплексных регрессионных испытаний на локальной хост-машине (со сквозным созданием изолированной базы данных `medical.db` и выводом детальных логов по каждому из 10 тест-кейсов) выполните в корне проекта следующую команду:

```bash
PYTHONUTF8=1 python -m pytest testing/lab10/test_automation.py -v
```

*   Флаг `PYTHONUTF8=1` принудительно включает поддержку UTF-8, предотвращая сбои кодировки `UnicodeDecodeError` при парсинге кириллических ФИО врачей из скриптов наполнения.
*   Флаг `-v` (verbose) выводит полные семантические имена функций тестов со статусом `PASSED`/`FAILED` вместо простых точек.

###  3. Облачный конвейер Непрерывной Интеграции (GitHub Actions)
В проект интегрирован декларативный CI-манифест `.github/workflows/main.yml`. При каждом push-запросе в ветки `develop` или `main` удалённый сервер Linux Ubuntu автоматически разворачивает окружение, накатывает СУБД и прогоняет пакет автотестов со статусом **Success / All checks have passed**.
