
Ответственность слоев и правила изоляции (Архитектурные запреты)

Чтобы избежать спагетти-кода и сохранить модульность, для каждого уровня жестко зафиксированы его обязанности и введены строгие запреты на выполнение чужой работы.

1. Presentation / Controller Layer (Уровень представления)

• Ответственность: Прием входящих HTTP/REST-запросов, проверка валидности входных параметров (проверка формата полиса ОМС, структуры JSON), управление сессиями, авторизация пользователей по ролям и формирование понятных ответов API.
• ⛔ Строго запрещено: Напрямую отправлять запросы в базу данных, выполнять бизнес-расчеты (например, проверять накладки в календаре) и хранить состояние системы.

2. Service Layer (Уровень бизнес-логики)

• Ответственность: Ядро медицинской системы. Реализует правила ТЗ: проверяет доступность врача, исключает конфликты времени (наложение слоев), управляет стадиями жизненного цикла приемов и инициирует внешние коммуникации (SMS/Email).
• ⛔ Строго запрещено: Работать со спецификой веб-фреймворка (читать HTTP-заголовки, куки), напрямую формировать HTML/JSON-ответы для пользователя или писать сырые SQL-запросы к БД.

3. Repository / Data Access Layer (Уровень доступа к данным)

• Ответственность: Изоляция работы с постоянным хранилищем. Предоставляет интерфейс для выполнения базовых CRUD-операций (создание, чтение, обновление, удаление) над медицинскими объектами. Отвечает за транзакции и выполнение эффективных запросов к таблицам.
• ⛔ Строго запрещено: Содержать правила бизнес-логики (например, проверять права Пациента на просмотр чужой ЭМК) и самостоятельно менять статусы заявок без ведома Сервиса.

4. Database Layer (Уровень хранения данных)

• Ответственность: Надежное и долгосрочное хранение информации, обеспечение ссылочной целостности (Foreign Keys), откат транзакций при сбоях и шифрование персональных данных по стандарту AES-256.
• ⛔ Строго запрещено: Отвечать за маршрутизацию пользователей, рассылать уведомления или выполнять логику приложения вне рамок базовых триггеров БД.
